## Implementation choices and residual risks

- Password and email timestamps persist in separate bounded JSON-encoded arrays in one InnoDB row per HMAC-SHA256 account key (resolved UsersT ID, existing JWT_SECRET as HMAC key, domain separation). Database clock, rolling 900-second window, oldest event ages out independently; a success does not erase earlier failures. Known aliases resolve to the same UserID. Unknown account names create no counter rows, and errors are generic; timing equivalence is not established. Keep the JWT secret consistent across instances; rotation changes rate-key namespace. Expired timestamps are pruned on subsequent writes; historical inactive rows remain and eventual bounded retention/cleanup should be reviewed separately. Account-level temporary lockouts can themselves be abused for denial of service; do not claim global/volumetric protection. No global ceiling was approved.
- Five failures permanently exhaust a specific challenge without falsely marking it verified. Other previously issued, unexpired challenges remain independently valid. Both clients share the same counter; existing cross-client verification contract is not changed. New login is required for an exhausted challenge. Existing authenticated sessions are not revoked by failures.
- Email reservation counts an attempted send even on delivery failure, to prevent retry abuse. Challenge creation and reservation commit before external email. Provider-side delivery cannot be rolled back.
- All IP headers are deliberately ignored by new controls. Prior R11/R19 and independent WA-PR-006 findings remain open. Render documents forwarded-address handling, but an actual trusted-hop/overwrite guarantee for all WA ingress paths is not verified. Do not set Express trust proxy globally, accept arbitrary forwarded headers, or group users by the proxy peer. A5 investigation is partial; 30/IP/15 minutes is **not implemented or active**. With explicit staged-probe authorization, compare two independent client networks and bounded spoofed-header requests through each actual ingress path (including direct onrender.com and any custom/proxy hostname). Use synthetic accounts/unknown names, no real IPs or secrets in retained reports, record only distinct/same sanitized correlation and whether spoofing affects the resolved identity. Confirm provider guarantees and the trusted hop policy; then approve exact resolver and enforce 30 requests/15 minutes, with regression tests for password reset. No such probe was executed. Review residual risk before production integration.
