## 2. Implementation contract and bounded choices

- `services/clientIp.js` is the shared narrow resolver. No global Express trust change; no use of X-Forwarded-For, req.ip, socket peer or arbitrary identity when provenance is absent. Only one syntactically valid CF-Connecting-IP raw-header occurrence is accepted under the configured verified-ingress gate. Duplicate/joined, scoped, malformed, missing or ungated values return null. Canonical IPv6 and IPv4-mapped IPv6 avoid spelling-based quota splitting. Private/loopback literal syntax is not itself evidence of provenance; only the external ingress gate is authoritative.
- Existing staging trust opt-in `WA_TRUST_RENDER_CF_IP=1` applies only to the exact existing staging origin. Production additionally requires the existing approved production environment/release contract and `WA_PRODUCTION_CF_INGRESS_VERIFIED=1`. The new production flag is an explicit operational assertion, not proof of provenance. Do not set it until the owner separately authorizes activation after confirming *all* accessible ingress paths reject or overwrite client-supplied CF-Connecting-IP and that the origin cannot be reached through an unverified path. Never infer production trust from staging evidence.
- New login quota activation `WA_LOGIN_IP_LIMIT_ENABLED=1` is off by default. It may be enabled in the separately authorized test environment only after the schema is applied and verified. A local direct request cannot manufacture staging trust. When identity is unknown, login IP counting is skipped; existing account/challenge protections still operate. No synthetic `unknown` key, shared proxy address or extra global login ceiling is introduced. The existing reset email and global ceilings remain in effect (5 and 100 per UTC-hour bucket, respectively). This is not a guarantee against broad volumetric abuse.
- New `LoginIpRateT` InnoDB table has one HMAC-SHA256 key per verified canonical IP, a bounded JSON-encoded event array and UTC update timestamp; no username/raw IP is stored. Using the existing JWT_SECRET with `login-ip-rate-v1|` domain separation follows the account/reset conventions. Every request reaching POST `/users/login` is counted before body validation and username lookup while the feature and provenance gates are enabled. 30 admitted requests per rolling 900 seconds; the 31st and later denied until an admitted event expires. Denials do not prolong the interval or grow the array. Exact boundary uses integer DB epoch seconds; subsecond granularity is not introduced. Requests rejected by upstream infrastructure or body parsing before the route are not counted.
- Upsert obtains the key lock; SELECT FOR UPDATE reads the row, and DB time is read **after** obtaining the lock. Parameterized update verifies one affected row. Commit the IP reservation independently before account lookup and existing account fence. This prevents a later account failure from refunding IP quota, avoids nesting a second connection inside an account transaction, and ensures unknown names consume quota without creating account records. No process-local state is used. Unexpected DB errors on verified/active quota fail closed rather than silently allowing the request. Error body for IP denial uses existing generic 401 `Invalid credentials or login temporarily restricted. Please try again later.` (same as unknown name/wrong password/account failure limit); existing email-issuance 429 message is unchanged. Reset route remains generic 200 for rate-denied and unknown email, and Origin denial remains 403.
- Reset IP limit remains 20 per existing UTC-hour bucket (not changed into a rolling window). It is applied only where resolver returns a verified identity. Existing independent reset email/global keys, deterministic lock ordering, increments on denied requests, transaction and external mail flow stay unchanged. IPv6 canonicalization may cause a one-time different key for a previously noncanonical spelling in the current hour; no historical counters are rewritten.
- Existing reset cleanup scheduler continues unchanged in cadence/behavior; add a bounded separate login-IP cleanup pass only when login feature enabled. Up to 12 batches of 250 expired rows (>48h stale) per daily run using UpdatedAt index, first run after existing 60s delay. Since 48h greatly exceeds the 15m rolling window, removed rows cannot contain active quota under the DB clock contract. Cleanup failures report only counts/safe labels and do not bypass enforcement. No new global scheduler or cleanup of accepted account-limiter rows.

## 5. Residual risk and release limits

- Production ingress assurance not completed. A boolean environment gate cannot by itself authenticate a header. Direct origin/alternative ingress must be covered independently before production enablement.
- Under unknown provenance, there is deliberately no login IP limit and no reset IP bucket; account/challenge/email/global controls remain. Unknown usernames can be attempted without an IP limit in that fallback. Shared public NAT can legitimately share a quota if provenance is verified; IPv6 address rotation/distributed attempts are not solved by a per-address quota. Existing reset global ceiling may be exhausted by aggregate abuse; do not conflate it with removed shared-proxy grouping. No global login limit authorized.
- DB row count scales with verified IP identities; bounded cleanup handles at most 3,000 expired rows/day per process. Observe retention/backlog and hosting capacity after authorization. No new account cleanup policy. HMAC secret rotation changes counter identities; use a consistent secret across instances and record rotation as a separate operational action.
- DB/server failures after IP reservation consume an admitted event by design. DB error handling is generic and must be verified in actual runtime. DB time changes backwards can safely reject a future stored event rather than bypass the quota. Existing production readiness / independent design review and 40-hour cumulative ceiling still apply; cumulative effort outside this continuation was not re-estimated.
